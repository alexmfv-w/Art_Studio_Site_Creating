# Контент-агент: правка и раздача постов — дизайн

Дата: 2026-08-06
Статус: одобрено художником в диалоге, готово к переносу в план реализации

## Контекст и масштаб

Студия «Кисть и Перо» ведёт бизнес через один канал (ВК) силами одного человека — художника. Ранее было решено делегировать администрирование как отдельный проект и вести контент на нескольких площадках (ВК открытая лента, ВК Donut, Telegram, Дзен, MAX — общий и гончарный каналы). Вручную писать, вычитывать и разносить один и тот же пост по всем площадкам — не масштабируется на одного человека.

Этот документ описывает **контент-агент** — модуль, который принимает черновик поста от художника, правит его орфографически и стилистически в её голосе, адаптирует под конкретные площадки и либо публикует сам (там, где это технически возможно), либо отдаёт готовый текст для ручной публикации (там, где нет API).

**Явно вне рамок этого документа** — большая централизованная система ведения бизнеса (курсы, запись на занятия, витрина работ, личный кабинет). Контент-агент проектируется как самостоятельный модуль, чьи данные и логика позже войдут в эту большую систему без переделки, но сам он не зависит от неё и может быть построен и запущен раньше.

## Разбивка площадок

| Площадка | Режим |
|---|---|
| VK — открытая лента | Автопубликация через API после подтверждения художником |
| VK Donut | Автопубликация через API после подтверждения художником |
| Telegram (канал студии) | Автопубликация через API после подтверждения художником |
| Дзен | Агент только готовит текст; художник копирует и публикует вручную |
| MAX — общий канал | Агент только готовит текст; вручную |
| MAX — канал о гончарстве | Агент только готовит текст; вручную |

Не каждый пост идёт на все площадки сразу — художник каждый раз указывает, для каких площадок предназначен конкретный черновик.

## Архитектура

Один постоянно работающий процесс (`content-agent`) на небольшом VPS. Использует long polling для Telegram (не webhook) — при таком объёме не нужен публичный HTTPS-домен и обслуживание TLS-сертификата, только исходящие соединения.

Внешние зависимости:
- **Telegram Bot API** — в двух ролях: (1) приватный диалог с художником (приём черновика, показ вариантов, кнопки согласования, планирование), (2) публикация в канал студии. Может быть один и тот же бот-токен, роли разделены логически.
- **VK API** — публикация на стену сообщества и в Donut (`wall.post` с соответствующим флагом); для медиа — отдельный цикл загрузки через `photos.getWallUploadServer` → загрузка файла → `photos.saveWallPhoto` → вложение в `wall.post`. Для отложенных постов используется нативный параметр даты публикации в `wall.post` — VK сам хранит и публикует пост в срок, независимо от того, работает ли наш сервис в этот момент.
- **LLM API (Claude)** — один вызов на черновик: правка текста в голосе художника + подготовка вариантов под выбранные площадки.
- **SQLite** — единственное хранилище данных сервиса (история постов, результаты публикации, профиль голоса, очередь отложенных Telegram-постов).

```
Художник → Telegram (приватный чат с ботом)
                │
                ▼
        content-agent (VPS, постоянный процесс)
        ├── LLM API (Claude) — правка + адаптация под площадки
        ├── SQLite — posts / publish_results / voice_profile / scheduled_jobs
        │
        ├── (после подтверждения) → VK API → открытая стена / Donut
        │      (медиа: скачать из Telegram → загрузить в VK)
        ├── (после подтверждения) → Telegram Bot API → канал студии
        │      (медиа: пересылка по file_id, без скачивания)
        └── (всегда) → текст для Дзен / MAX-каналов — в чат художнику, копирует сама
```

**Планировщик.** VK умеет откладывать публикацию сам (штатный параметр `wall.post`). Telegram Bot API так не умеет — планирование постов доступно только обычным аккаунтам, не ботам. Поэтому для Telegram сервис ведёт свою очередь (`scheduled_jobs`) и фоновым циклом (проверка раз в минуту) сам вызывает публикацию в нужный момент. Это дополнительный аргумент в пользу постоянно работающего процесса, а не serverless-функций.

## Формат ввода

Художник присылает боту одним сообщением: текст черновика, либо фото/видео (в том числе альбом) с подписью — подпись и есть черновик текста. Агент правит только текст, медиа не анализирует и не изменяет, только передаёт дальше.

**Особенность Telegram-альбомов.** Когда пользователь отправляет несколько фото одним альбомом, Telegram доставляет их боту не одним сообщением, а несколькими отдельными обновлениями подряд (с общим полем `media_group_id`), причём подпись обычно прикреплена только к одному из них. Чтобы не запускать обработку черновика по каждому фото отдельно, сервис буферизует входящие сообщения с одинаковым `media_group_id` в течение ~1.5–2 секунд и только после паузы без новых сообщений считает черновик собранным целиком.

## Сценарий диалога (state machine)

Состояние диалога хранится в SQLite, не только в памяти процесса — перезапуск сервиса не должен терять черновик или его этап.

1. **`DRAFT_RECEIVED`** — художник прислала текст и/или медиа. Сервис дожидается сборки альбома (если применимо).
2. Бот задаёт два коротких вопроса тапами:
   - «Для кого пост?» → `🎨 Взрослым` / `🧒 Детям` / `👥 Оба` — метка сохраняется для будущей аналитики, на маршрутизацию сейчас не влияет (площадок под каждую аудиторию отдельно пока нет).
   - «Куда публикуем?» → мультивыбор тумблерами по списку из шести площадок, кнопка «Готово».
3. **Один вызов LLM** с профилем голоса + черновиком + списком выбранных площадок → структурированный результат: основной выправленный текст плюс лёгкие варианты под конкретные площадки (обрезка длины, снятие хэштегов для ручных площадок и т.п.). Состояние → **`REVIEW`**.
4. Бот показывает результат:
   - Если выбраны VK и/или Telegram — одно сообщение с текстом и кнопками `✅ Опубликовать` / `✏️ Переписать` / `❌ Отмена`.
   - Если выбраны Дзен и/или MAX-каналы — отдельным сообщением текст в моноширинном блоке под каждую площадку (без кнопки публикации, просто для копирования).
5. **`✅ Опубликовать`** → бот спрашивает время: `Сейчас` / `Через 1 час` / `Завтра в 10:00` / `Указать время` (свободный текст).
   - Немедленно или по расписанию для VK: вызов `wall.post` (с `publish_date`, если отложено) → VK сам публикует в срок.
   - Немедленно для Telegram: прямой вызов API.
   - По расписанию для Telegram: запись в `scheduled_jobs`, фактическая отправка — фоновым циклом в нужный момент.
   - Состояние → **`PUBLISHING`** или **`SCHEDULED`**, затем **`DONE`** — отчёт по каждой площадке отдельно (успех/ошибка), провал одной не блокирует остальные.
6. **`✏️ Переписать`** → бот спрашивает коротким текстом, что поправить → повторный вызов LLM с этой правкой поверх черновика → снова `REVIEW`. Цикл повторяем.
7. **`❌ Отмена`** → черновик помечается отменённым, состояние → `IDLE`.

Дополнительно: команда вроде `/otlozhennye` — список ещё не вышедших отложенных постов с кнопкой отмены на каждый.

## Модель данных (SQLite)

**`posts`** — одна строка на черновик/пост:
- `id`, `created_at`, `status` (`draft` / `review` / `scheduled` / `published` / `failed` / `cancelled`)
- `audience` (`adults` / `kids` / `both`)
- `raw_text`, `edited_text`
- `media` — список Telegram `file_id` с порядком (для альбома)
- `targets` — отмеченные площадки (`vk_wall`, `vk_donut`, `telegram`, `dzen_text`, `max_general_text`, `max_pottery_text`)
- `scheduled_at` — время публикации, если отложено (`NULL` = сразу)

**`publish_results`** — одна строка на пару «пост × площадка», отдельно от `posts`, чтобы частичный отказ одной площадки не путался со статусом всего поста и чтобы можно было повторить публикацию только для упавшей площадки:
- `post_id`, `target`, `status` (`pending` / `sent` / `failed`), `external_id` (id поста на площадке — признак того, что публикация реально прошла), `error`, `attempted_at`

**`voice_profile`** — описание тона + подборка примеров реальных прошлых постов художника из ВК (собирается один раз через VK API, обновляется вручную по мере необходимости).

**`scheduled_jobs`** — только для Telegram (у VK — собственное планирование, отдельная очередь не нужна): `post_id`, `target`, `fire_at`, `status`.

## Обработка ошибок

Разделение на «можно повторить самому» и «нужен человек» — чтобы сервис не долбился бесконечно там, где сам не разберётся.

- **Сбой LLM-вызова** (таймаут, временная ошибка) — одна автоматическая попытка повтора, затем сообщение художнику с кнопкой `Повторить`. Черновик не теряется, остаётся в `posts`.
- **Сбой публикации** — сетевые/5xx-ошибки: одна автоповторная попытка. Ошибки авторизации (просроченный/отозванный токен) — сразу `failed` с понятным текстом «нужна помощь разработчика», без бесконечных попыток. Кнопка `Повторить публикацию` бьёт только по упавшей площадке — наличие `external_id` у других защищает от повторной публикации/дублей.
- **Сервис упал посреди публикации** — при старте сервис проверяет `publish_results` на зависшие `pending`-строки без `external_id` и докладывает только их.
- **Пропущенный отложенный пост** (сервис не работал в момент срабатывания) — при старте публикует просроченное сразу и явно предупреждает художника о задержке.
- **Скачивание медиа для VK не удалось** (устаревшая ссылка Telegram) — запрашивается свежий путь к файлу непосредственно перед загрузкой в VK; при повторной неудаче — просьба прислать медиа заново.

## Тестирование

Пропорционально размеру инструмента (один пользователь, несколько постов в неделю) — без избыточной инженерии.

**Юнит-тесты (чистая логика, без живых API):**
- Группировка альбома по `media_group_id` и окну ожидания
- Сборка промпта для LLM
- Адаптация текста под площадку (обрезка длины, снятие хэштегов)
- Переходы состояний диалога, включая циклы «переписать»/«отмена»
- Логика докачки после сбоя — по набору `publish_results` корректно определяет, что повторить

**Интеграционная проверка на тестовых, но настоящих аккаунтах** (не моках): отдельный тестовый Telegram-канал и тестовая VK-группа. Чек-лист перед переключением на боевые каналы: одиночное фото, альбом, текст без медиа, отложенный пост в VK, отложенный пост в Telegram, имитация сбоя авторизации VK, убийство процесса посреди публикации (проверка додела без дублей).

**Качество текста от LLM** — не pass/fail проверка. Фиксированный набор реальных прошлых черновиков как контрольные примеры, ручная сверка глазами при изменении промпта или профиля голоса.

**Специально не делаем:** нагрузочное тестирование, CI с целевым покрытием, полное мокирование внешних API — не пропорционально размеру системы.

## Открытые вопросы на этап реализации

- Выбор языка/рантайма сервиса (Python или Node) — не принципиально для дизайна, решается на этапе плана реализации.
- Как именно художник указывает произвольное время при «Указать время» — формат парсинга свободного текста уточнить в плане.
- Процедура первичного сбора `voice_profile` из архива ВК — разовый скрипт или ручная выборка постов, уточнить в плане.
